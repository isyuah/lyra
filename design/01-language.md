# 01｜写一段 Lyra：语法与类型设计问卷

**先填 L-01～L-03。** 三题分别决定函数怎么读、赋值后什么会变、库 API 怎么连起来。每题的「我的选择」可以填方案、改写示例，或写「暂缓」。如果选项太死，直接写你想让哪一行通过、哪一行报错，比选字母更有用。

[原草稿](../RFC_draft.md)把 struct 值语义 / class 引用语义、默认非空、支持 Attribute 与 AST 宏但不开放任意语法扩展列为 Accepted；成员级复制、`T?` 与 `Option<T>` 等价等细节仍是 Proposed。这里沿用那些方向来检验例子；所有新写法与推荐都是候选，你也可以明确提出重开已有方向。

## 第一轮：日常写代码的手感

### L-01｜函数体已经说明返回什么，还要不要写返回类型？

```text
fn badge(score: Int) {
    if score >= 60 { "通过" } else { "未通过" }
}

pub fn title(score: Int) -> String { badge(score) }
```

草稿的 `maximum` 和 `start_server` 都省略了末尾的 `return`。建议统一为：块的末个表达式就是值，`return` 用于提前离开函数。比如把上面的 `if` 直接写进声明返回 `String` 的 `title`，再把 `else` 改成数字，错误就应指向那个数字，说明此分支预期返回 `String`。

- **A（建议）：** 具名函数写参数类型；局部变量、lambda 和私有非递归函数的返回类型可推断，公开或递归函数写返回类型。私有 `badge` 很短，给别人用的 `title` 则有一行能读完的契约。
- **B：** 也允许推断公开函数的返回类型。少写一遍 `String`，但改函数末行就可能改了别的包看到的 API。

我的选择：A,对了返回值标注能否换成不需要->,而是通过:或者干脆不需要额外符号

### L-02｜`let` 是不许换掉这个值，还是不许通过它修改对象？

沿用草稿的 `Profile`（struct，含 `var name: String` 和 `var owner: User`）与 `User`（class，含 `var name: String`）。下面前三行之后，你期待第 4、5 行各发生什么？

```text
let first = Profile(name: "原稿", owner: user)
var copy = first
copy.name = "修订稿"
first.owner.name = "Ada"
first.name = "定稿"
```

- **A（建议）：** 第 4 行通过，`copy.owner.name` 也变成 `"Ada"`；第 5 行报错。struct 复制自己的字段值，class 字段复制引用；`let` 禁止改写 `first` 这个值，不会冻结它引用的 `User`。这符合草稿 §1.4–1.5 的提案，但别名修改确实可见。
- **B：** 保留同样的复制规则，但 `let` 同时提供只读视图，第 4、5 行都报错。其他可写别名仍可以修改 `User`；语言需要区分哪些方法能通过只读视图调用。

我的选择：我希望是禁止修改值,但是可以修改引用,另外我希望是val var.而不是let var,或者可以让let是var的别名

### L-03｜你希望作者怎样给已有类型加上一套好用的 API？

假设 `filter`、`map` 是第三方库写的，`users` 的集合类型没有预先定义它们。以下是同一个操作的两种拼法：

```text
users.filter { it.active }.map { it.name }
users |> filter(user -> user.active) |> map(user -> user.name)
```

- **A（建议作为第一套常用写法）：** 方法链 + 导入的扩展函数 + 尾部 lambda。末个形参是函数类型时，传入的 lambda 可以放在括号外；期望恰好一个参数时可用 `it`。两个都省略参数名的单参数 lambda 嵌套时，`it` 指内层；要用外层参数就为它起名。代价是点号后的名字可能来自导入，不只来自类型定义。
- **B：** 管道 + 普通函数。`value |> f(arg)` 把左侧表达式的结果作为 `f` 的第一个参数，调用点直接写出函数名，不用设计库扩展方法的查找规则。代价是库 API 需要约定数据参数的位置。

两者可以并存，但最好写明哪一个是标准库示例的默认风格。选 A 时建议：能匹配的实例方法优先；两个同优先级的扩展都适用就报歧义，列出两个导入来源，不能让导入先后改变结果。隐式 `it` 只代表参数，不顺带引入能省略 `this.` 的隐式接收者。

我的选择：A

## 第二轮：用边界例子定语义

### L-04｜带名字的参数换了位置，有副作用的代码按什么顺序执行？

```text
fn join(left: Int, right: Int) -> Int { left - right }
join(right: mark("R"), left: mark("L"))
```

`mark` 先记录传入的字母，再返回一个整数。**建议（A）：** 允许按名字换位，仍然按调用处从左到右各求值一次，日志为 `R, L`；名字只决定值传给谁。**备选（B）：** 命名参数也必须按声明顺序写，上面的调用直接报错；读者少记一条换位规则，调用者少一点组织长参数表的自由。此题对应草稿 P0-11，也决定链与管道展开时能否交换副作用。草稿已写明 `??` 短路，未选中的右侧不参与这里的求值。

我的选择：支持命名参数和默认值,以及变长参数,允许按名字换位置

### L-05｜第三方类型有 `render` 方法，就能传给要求 `Render` 的函数吗？

```text
trait Render { fn render(self) -> String }
fn draw<T: Render>(item: T) -> String { item.render() }
class Badge { fn render(self) -> String { "NEW" } }
draw(Badge())
```

草稿 P0-01、P0-08 实际有两个独立选择，可以分开填：

- **谁符合接口：显式声明（建议）/ 方法签名符合即自动满足。** 前者拒绝示例的最后一行，提示 `Badge` 尚未声明实现 `Render`；后者直接接受，适配现成类型方便，但碰巧同名同签名的方法也会被当成承诺。
- **怎么复用实现：组合和接口默认方法（建议）/ 另加带状态的 class 单继承。** 前者用字段持有可复用对象，有时得写转发方法；后者可覆盖父类行为，但构造顺序、哪些方法可覆盖也要有规则。

`T: Render` 在这里解决的是泛型约束。若实际程序还要把不同类型装进同一个 `List` 并逐个 `render`，请注明；那需要能在运行时分派的接口值，不只是给泛型换一个名字。两种接口用法都不要求用户选择泛型如何生成机器码。

我的选择：如果鸭子类型的性能和复杂度等代价可以接受,我更喜欢鸭子类型,喜欢组合和接口.

### L-06｜一个可空字段的「没传」和「传了 null」，是否能用普通泛型区分？

以更新昵称为例：客户端可以保留原值、清空昵称、设新昵称。如果草稿 §7.2 的 `T? = Option<T>` 成立，就能这样表示三种状态：

```text
fn describe(change: Option<String?>) -> String {
    match change {
        None             => "保留原值"
        Some(None)       => "清空昵称"
        Some(Some(name)) => name
    }
}
```

- **A（建议）：** `Option` 是可嵌套的普通枚举，`null` 是由目标类型确定的 `None`；上例漏掉 `Some(None)` 时，编译器指出缺少哪种情况。有明确目标 `String?` 时允许直接传普通 `String`。要表示「传了 null」，仍须写 `Some(null)`。不必为此马上引入容易与 `??` 混淆的 `T??` 拼写。
- **B：** `T?` 是语言内置的可空类型，重复可空合并为一层。通常的 API 更扁平；上述三态显式使用业务枚举，如 `PatchField<String?>` 的 `Omitted` 和 `Set(value)`，不把区别交给可空嵌套。

我的选择：A

### L-07｜写下 `@trace`，直接调用这个函数时应该发生什么？

`@route("/users")` 可以只是路由表读取的资料，`@derive(Json)` 可以请求生成序列化实现；两者都没有回答 `@trace` 能否让**每次直接调用**自动记一条日志。任选你实际需要的最小能力：

- **A（建议起点）：** 保留草稿的 Attribute 与受控 AST 宏方向；先覆盖元数据和 `derive`，普通包可通过高阶函数显式包装，如 `router.get("/users", trace(users))`。这里走路由时有日志，直接调用原来的 `users()` 没有。代价是注册点需要写包装。
- **B：** 允许声明上的宏在编译期改写函数体来插入日志，直接调用也记录。宏需要保留用户源位置，让报错能从生成代码跳回 `@trace`。
- **C：** 增加运行时函数装饰器：普通库函数就能替换声明所绑定的函数，直接调用也记录。要规定何时执行包装，以及 `@trace` 与 `@auth` 叠加时谁先收到调用。

如果你最想做的其实是路由、校验、序列化或其他框架，填一个真实例子即可；没有必要仅仅因为三者都写作 `@` 就一次实现三个机制。

我的选择：我希望,首先至少支持函数装饰器,但是我有一个要求就是以后和JSON TOML等做数据交换的时候,我不希望需要手动声明如何序列化和反序列化,更喜欢类似js go kotlin那种方式,尽量简单些

### L-08｜整数加一越界时，你希望 Debug 和 Release 都发生什么？

```text
fn bump(value: Int32) -> Int32 { value + 1 }
```

给 `bump` 传入 `2_147_483_647`。**A（建议）：** 普通整数算术两种构建都报告溢出，并定位到加号；需要按固定位宽回绕时显式使用回绕运算。服务里的计数异常更容易排查，有些运算会多一道检查。**B：** 普通运算都按照固定宽度回绕，这里得到 `-2_147_483_648`；需要检查时显式调用检查运算。不要让默认结果随优化级别变化。这个例子故意用 `Int32` 固定宽度；无后缀 `Int` 的宽度可在平台目标明确后单独定。

我的选择：A

## 可对照的现有设计

- [Kotlin：lambda 与尾部参数](https://kotlinlang.org/docs/lambdas.html)分别说明尾部 lambda 和单参数的隐式名 `it`。可以借日常写法，不必连隐式接收者也一起采纳。
- [Go 规范：实现接口](https://go.dev/ref/spec#Implementing_an_interface)用类型集定义何为实现接口；只要求方法的接口是 L-05 中「不另写实现声明」的现成参照。
- [Rust Reference：过程宏](https://doc.rust-lang.org/reference/procedural-macros.html)区分为输入类型追加声明的 derive 和可替换目标声明的属性宏。这个区分对 L-07 有用，不涉及照搬其 token 输入格式。
