## 第一批：补齐语言骨架

### SYN-01 ★ · 返回类型用什么标记？

已确认公开和递归函数需要标注，局部和合适范围内的私有函数可推断；只问标记形式。对比：

```text
fn title(score: Int): String { ... }
fn title(score: Int) -> String { ... }
```

- **A（建议）：** 用 `: String`。参数和返回类型都用冒号，写法一致；调用处和声明处不相混，因为返回标记在参数列表之后。
- **B：** 用 `-> String`。返回方向更醒目，但与参数类型分隔符不同。
- **C：** 用无标记的 `String`，即 `fn title(score: Int) String`。少一个符号，但嵌套函数类型和后续声明扩展要特别审查歧义。

我的选择：A

### SYN-02 ★ · 默认参数和变长参数怎样组合？

命名参数可换位、实参表达式按源码顺序求值已确定；还需确定合法调用形状和默认值的求值时机。例：

```text
fn connect(host: String, port: Int = default_port(), tags: String...) { ... }
connect(port: choose_port(), host: choose_host())
connect("db.example", "primary", "readonly")
```

- **A（建议）：** 位置实参必须在命名实参前；同一形参最多绑定一次。默认表达式仅在调用缺省该值时执行，按形参声明顺序执行，且只能引用更早的形参。变长参数必须是最后一个形参，只收位置实参；要整体传入集合时使用显式展开语法。
- **B：** 允许命名实参后继续填尚未绑定的形参；优先便于生成调用，代价是调用绑定规则更复杂。
- **C：** 变长参数也可按名字传集合，重复命名参数可逐个追加；调用处表达更灵活，但必须另外规定类型及展开语法。

如果你想采用别的规则，请写一条“通过”和一条“报错”的调用例，并说明默认表达式副作用的执行顺序。

我的选择：A

### SYN-03 ★ · 换行、分号和块末表达式怎样解析？

块以最后一个表达式作为值已确定；分号和换行是否形成语句边界仍未定。

- **A（建议）：** 分号可省；换行在语法上能结束一个完整语句时作为分隔，运算符、点号或逗号等未完成表达式可继续到下一行。块最后的表达式不加分号才产生值；加分号的语句不产生值。
- **B：** 换行不分隔表达式；多个语句必须用分号。解析容易一致，手写代码更像传统 C 风格。
- **C：** 换行总是分隔语句；跨行表达式必须用显式续行符或括号。

最好补充这两行谁应通过：

```text
val total = price
    + tax
```

```text
if ready { start() }
next()
```

我的选择：A

### SYN-04 ★ · 分支、循环和模式匹配的返回规则？

- **A（建议）：** `if` 在值位置必须有 `else`；`match` 对 sealed enum/Option 必须穷尽；普通循环返回 `Unit`；需要遍历值时使用显式集合 API。
- **B：** `if` 没有 `else` 时返回可空值；省略分支更短，但容易把漏写逻辑伪装成空值。
- **C：** `match` 可非穷尽，未命中时抛异常；扩展枚举成员容易，但错误更晚暴露。

模式匹配还需说明：是否支持守卫条件、类型测试、解构 Struct、忽略项 `_`，以及不完整匹配是编译错误还是警告。条件表达式是否必须为 `Bool`，还是接受 truthy 值？建议必须是 `Bool`，避免不同类型暗藏转换规则。

请补充是否支持 `for` / `while` / `loop`，`break` 和 `continue` 能否带值、是否允许标签，以及如何迭代自定义类型。

我的选择：A

### SYN-05 ★ · 是否加入管道运算符？

你选择了扩展函数和方法链作为日常 API 风格；是否仍要在核心语法加入 `|>`：

```text
users.filter { it.active }.map { it.name }
users |> filter { it.active } |> map { it.name }
```

- **A（建议）：** 首版不加内置 `|>`；需要函数组合时使用普通函数或标准库 API，避免重复设计扩展查找和调用展开规则。
- **B：** 增加 `x |> f(args)`，定义为 `f(x, args)`，左侧只求值一次，优先级低于算术和成员访问。
- **C：** 增加链式管道 `x |> f |> g`，每步都把左侧作为唯一参数；多参数调用必须使用显式闭包。

我的选择：a

### SYN-06 ★ · `?` 能否同时传播 `Result` 与 `Option`？

`Result` 的 `?` 错误传播已接受；Optional 是否共用拼写仍开放。对比：

```text
fn find_name(id: Int): String? {
    val row = find_row(id)?
    row.name
}
```

- **A（建议）：** 同一 postfix `?` 支持两者：`Result::Err` 传播错误；`Option::None` 从返回兼容的 Optional 函数提前返回 None。两种作用的返回类型由静态类型确定，不能相互转换。
- **B：** `?` 只用于 `Result`；Optional 使用 `match`、`or` 等明确 API，避免同一符号传播不同状态。
- **C：** `?` 都支持，但只在返回类型完全一致时可用，不做错误提升或 Optional 类型提升。

我的选择：A

### SYN-07 · 扩展函数冲突时，如何寻找方法？

实例方法优先、同优先级扩展歧义时报错且不依赖导入顺序已接受。请确认剩余规则：

- **A（建议）：** 按接收者静态类型解析扩展；只考虑当前模块和显式导入的候选。扩展函数不运行时动态分派；`it` 不引入隐式接收者。
- **B：** 也从包内所有可见扩展自动参与候选。少写导入，但更容易因依赖新增方法产生歧义。

扩展方法能否访问接收者私有成员？是否允许扩展属性？

我的选择：A,拓展方法,如果我们要做比较彻底的话,是否可以考虑能够访问私有成员?就是真的拓展方法,而不是函数调用的语法糖

### SYN-08 · Trait、泛型和异构接口的拼写？

静态结构匹配已确定：具备匹配成员即可满足泛型约束。以下仍是候选：

```text
fn draw<T: Render>(item: T): String { ... }
val items: List<dyn Render>
```

- **A（建议）：** 选定一种统一的 `trait` 词汇；约束列表用 `T: Render`。异构接口值使用显式 `dyn Render` 或等价装箱类型，首版只支持明确的接口对象转换。
- **B：** 统一使用 `interface`，并用单一写法表达泛型约束和运行时接口值。

泛型支持函数、Struct、Class、集合和 async Task 是否都属于首版语言契约？哪些高级特性可留后？（例如关联类型、变型、特化、递归约束。）

我的选择：A,你说的这几个泛型支持函数、Struct、Class、集合和 async Task都属于首板版语言契约

### SYN-09 · 声明、枚举和构造器采用什么骨架语法？

草稿包含 `struct`、`class`、`enum`、`trait`，但模块导入、枚举分支、构造和属性访问的完整语法未冻结。

- **A（建议）：** 统一大括号块；枚举区分无载荷与带载荷分支；Struct 使用命名字段构造；Class 使用显式构造函数；不自动生成继承关系。
- **B：** 使用关键字参数形式的构造调用（如 `User(name: "Ada")`），不单独写工厂语法。
- **C：** 字段构造只允许 Struct；Class 必须通过构造器/工厂函数创建，以便将来验证不变量。

请写一组想要的 enum 声明、一个带数据的分支和对应 `match`，并指出 Class 初始化代码中哪些场景需要禁止。

我的选择：A
Enum 声明与 match 示例：

代码段
enum FetchResult {
    Pending,                          // 无载荷分支
    Ok(status: Int, body: String),    // 命名字段载荷
    Err(String),                      // 位置载荷
}

fn handle(res: FetchResult) {
    match res {
        Pending => log("加载中"),
        Ok(status, body) => print("${status}: ${body}"),
        Err(msg) => panic(msg),
    }
}
Class 初始化代码中必须禁止的场景（Definite Initialization 检查）：

全路径初始化前读取字段：在所有非空字段完成赋值前，禁止读取 self.field。

self 提前逃逸（最关键）：在所有字段赋值完成前，禁止将 self 传给外部函数、存入全局变量、捕获进闭包或异步任务（spawn），也禁止调用依赖完整状态的实例方法（避免并发任务或外部代码看到未初始化完的半成品对象）。

分支遗漏与中途提前返回：if / else 或 match 分支必须保证所有执行路径都完成了字段初始化；禁止在初始化完成前使用 return 提前退出。

### SYN-10 · 操作符可否重载，怎样固定优先级？

- **A（建议）：** 只允许有明确标准含义的有限操作符重载；不允许定义新优先级或新增符号。库 API 默认用普通方法，比较/算术遵循通用契约。
- **B：** 可将现有运算符绑定到任意用户函数；表达力强，但每个运算符都需有规则和诊断。
- **C：** 另引入可声明的优先级组；语法 DSL 能力更强，解析器、格式化和跨包阅读更复杂。

特别说明 `==`、`<`、`+` 是结构相等、调用 Trait 还是按类型内置；优先级和结合性必须有固定表，不得随导入变化。

还需固定算术、比较、逻辑、成员访问、`?.`、`??`、`?`、赋值的优先级及左右结合性；短路操作的求值顺序；除函数实参之外二元表达式、接收者和赋值两侧是否都左到右、各求值一次。

我的选择：B,类似C++那种,但是可以禁止重载短路运算符（&&、||、??、?.）禁止重载基础赋值 =、成员访问 . 和错误传播 ?以及 == 和 < 采用“核心 Trait + 自动派生”

### SYN-11 · 数值字面量及 `Int` 的平台宽度？

- **A（建议）：** `Int8/16/32/64` 等固定宽度整数；无后缀 `Int` 固定为 64 位；字面量先按上下文检查，溢出编译失败。普通运算的运行时溢出仍按已接受规则检查。
- **B：** 无后缀 `Int` 随平台字长变化；更接近指针运算，但同一程序在不同目标上可能有不同范围。

还需定：浮点默认类型、整数到浮点是否隐式转换、精度损失处理、十六/二进制字面量及无符号整数是否为首版能力。

我的选择：A
浮点默认类型：无后缀浮点字面量（如 3.14）默认为 Float64（Float 为 Float64 的内置别名）；同时提供 Float32（支持 3.14f32 后缀或上下文类型推导）。

整数到浮点的转换：禁止运行时变量隐式转换（如 Int 不能隐式传给 Float 参数，必须显式调用 x.toFloat()），防止 64 位整数转 53 位尾数浮点时静默丢失精度；但无后缀整数字面量在目标类型明确为浮点时（如 val f: Float = 0），允许直接按目标浮点类型解析。

精度损失与窄化处理：所有可能丢失精度或溢出的转换（Int64 -> Int32、Float64 -> Float32、Float -> Int）一律禁止隐式发生，必须通过显式方法表达意图（如 toInt32Checked() -> Int32? 检查溢出，或显式截断）。

进制字面量与无符号整数（首版纳入）：

首版支持十六进制（0xFF）、二进制（0b1010）、八进制（0o755）字面量及数字下划线分隔符（1_000_000）；

首版提供 UInt8、UInt16、UInt32、UInt64 及 64 位 UInt（用于字节缓冲、位运算与 C FFI 交互），日常业务计算默认推荐有符号 Int。

### SYN-12 · 字符串、字符和插值写法？

候选包括普通双引号、单字符类型、转义、原始多行字符串、模板插值（如 `"Hello, ${name}"`）。

- **A（建议）：** 双引号表示 String，单引号表示单 Unicode scalar 字符；`${expr}` 插值；原始/多行字符串采用单独明确的分隔符。
- **B：** 首版不提供模板插值，使用格式化 API，减少词法边界和转义规则。

需特别决定插值内的引号/大括号怎样配对、格式化如何报类型错误、是否支持字节字符串。

我的选择：A
插值内的引号与大括号配对：词法分析器采用状态栈嵌套扫描。扫描到 ${ 时压入表达式状态并启动花括号层级计数；插值内部允许正常出现嵌套双引号字符串（如 "user: ${map["name"]}"）以及成对的花括号块（如对象字面量或条件块），直到匹配的闭合 } 将层级归零后才恢复外层字符串扫描。原始字符串（如 r#"..."#）不触发转义与 ${} 插值。

格式化的类型错误诊断：${expr} 在类型检查阶段统一约束 expr 必须满足内置 Display Trait（即具备 fn to_string() -> String 签名）。若传入未实现该方法的类型，编译器在前端 check 阶段直接将波浪线定位在 ${expr} 内部的表达式处，明确报告“类型 X 未实现 Display，无法用于字符串插值”。

字节字符串支持：首版支持，采用 b"..."（及原始字节串 br#"..."#）前缀写法，求值类型为只读字节序列（如 Bytes / Slice<UInt8>），不要求合法 UTF-8，支持 \xHH 十六进制字节转义，用于网络协议解析与 C FFI 缓冲区传参。

## 第二批：类型与控制流语义

### TYPE-01 ★ · `Any` 到底保证什么？

“支持 Any”已确认；它是何种类型仍开放。

## 第四批：模块、包和构建工具

### MOD-01 · `pub import` / re-export 的精确规则？

- **A（建议）：** 普通 `import` 只在当前模块可见；只有显式 `pub import X as Y` 才成为当前模块可导出的名字。公开别名不能把私有原类型提权；冲突必须由源码消解，导入顺序无优先级。
- **B：** 模块必须有显式 export 清单；内部拆文件较易重构，但要维护一个公开入口文件。

未公开宏生成的声明可否被同模块其他文件使用？宏能否生成 `pub` 声明、需要谁批准？

我的选择：A

### MOD-02 ★ · 清单、版本约束和锁文件格式？

- **A（建议）：** 使用机器可读 TOML 清单；依赖使用语义化版本范围和显式来源，workspace 锁文件精确记录来源、版本、校验摘要。已有锁不主动更新；`--locked` 和 `--offline` 语义保持 RFC 中的定义。
- **B：** 清单用专用 DSL；可做类型/条件校验，但工具链首版必须实现另一套解析器。

版本约束是否用 SemVer；允许哪些范围（精确、caret、区间）；如何处理 prerelease、Git 依赖和本地路径？推荐正式发布包不得依赖机器本地路径。

我的选择：暂时JSON5吧

### MOD-03 · 包中心首版的信任、命名和撤回规则？

- **A（建议）：** 包身份由明确来源 + 完整包名组成；同身份同版本不可覆盖；发布内容摘要进入锁；首版可以先实现一个公共中心，签名与私有中心留后续 RFC。
- **B：** 首版就要求发布签名和私有中心支持；信任边界更完整，但中心客户端、密钥轮换和访问控制也成为首版阻塞项。

如何处理 yanked/撤回版本（旧锁能否继续安装）、包名抢注、恶意版本举报，以及维护者账号恢复？

我的选择：A

### MOD-04 · 第三方构建脚本怎样被授权？

默认构建不执行脚本、授权前展示来源和脚本已接受。

- **A（建议）：** 每个包/脚本版本单独授权并绑定内容摘要；授权记录可查看/撤销。CI 非交互运行时缺授权就失败。首版隔离权限按最小能力（文件目录、网络、子进程）声明。
- **B：** 用户一次信任某包的未来全部版本；操作少，但升级后授权也继续生效。
- **C：** CI 提供集中 allowlist，开发机逐次确认；便于自动化且不信任更新版本。

离线模式、缓存、脚本产物摘要、脚本失败后是否保留部分产物如何处理？

我的选择：

### MOD-05 · 构建结果要保证到什么程度可复现？

- **A（建议）：** 锁文件保证依赖选择；单独工具链版本文件固定 compiler/stdlib/LLVM 版本。完整字节可复现作为工程目标，首版不承诺跨宿主完全同字节。
- **B：** 锁文件同时固定所有工具链、linker、SDK、环境变量和构建脚本输入，并要求 bit-for-bit 复现；可审计更强，初期工程成本大。

哪些目标选项、C 系统库和环境变量必须进入构建摘要？发布包要否包含编译器版本和 SBOM？

我的选择：A

## 第五批：原生运行时、FFI 与诊断

### NAT-01 ★ · 首期 Linux 目标基线？

已确认 Windows + WSL 构建、部署 Linux、允许动态链接；仍未选架构和 libc。

- **A（建议）：** 首期 Linux x86-64 / glibc；在实现机与目标服务器覆盖面更广后，再增加 ARM64 和 musl。动态依赖必须列出。
- **B：** 首期 x86-64 / musl；交付更独立，但系统库兼容和本机 C 库互操作可能更费工作。
- **C：** 同时支持 glibc 和 musl 两条目标；覆盖广，但扩张测试矩阵。

首个验收服务器是哪类 Linux 发行版/最低版本？是否需要 arm64？是否把 scratch/静态链接明确放到后续？

### NAT-02 ★ · GC 原型先用哪种路线？

语言语义不依赖回收时机已接受；具体 GC/LLVM Root Tracking 未定。

- **A（建议）：** 先原型评估成熟的非移动保守 GC（如 BDWGC），以最快拿到 LLVM AOT + GC 纵向切片；语言不承诺对象地址稳定，FFI 使用句柄/固定边界。必须以优化构建、异步帧和 C 线程注册通过压力测试作为准入条件。
- **B：** 首版直接做精确 Root Tracking；内存可控、少保留垃圾，但 LLVM safepoint、状态帧和优化交互会先成为主要实现工作。
- **C：** 先以引用计数原型验证语言，但循环引用、弱引用和跨任务周期要另加处理，不符合最终方向时需要重做。

建议先确认哪些是语言契约，GC 供应商在原型对比后再选；你是否接受首个可运行版本采用 A？是否有对象稳定地址、暂停时间或单进程内存的硬约束？

我的选择：A，但是以后一定会演进到B

### NAT-03 · C 声明、指针、句柄和错误如何跨边界？

- **A（建议）：** 原始 extern/pointer API 标为 `unsafe`/不安全模块；官方或社区包提供安全封装。受管理对象传 C 使用明确的句柄或 pin；字符串/数组所有权和长度显式表示；C 错误码在封装层转换为 `Result`，Lyra 异常不得越过 C ABI。
- **B：** 允许高层类型直接映射 C 参数并自动复制；调用简洁，但内存分配和性能行为更隐式。

SQLite 首版只需打开、prepare/bind/step/finalize/close，不支持 C 外线程回调已选定。C callback、C 保存 Lyra 闭包、C longjmp 等能力是否暂缓？

我的选择：A

### NAT-04 · GC、调度器和 Runtime 要暴露哪些资源控制？

- **A（建议）：** 默认 Worker 和 GC 策略由 Runtime 管理；公开最小的 heap/worker 限制和统计快照接口，具体指标稳定性与配置语法另行规范。不得承诺某个内存占用数字，先用等价负载和 Go 对照测量。
- **B：** 首版只提供全局默认，所有监控和调优延后。
- **C：** 允许每个程序在源码/清单中配置所有线程、堆、GC 和暂停参数。

你的部署最希望限制的是总 RSS、并发线程、GC 暂停还是二进制大小？是否有真实服务器容量作为基线？

我的选择：A

### DIAG-01 ★ · 编译错误和运行时栈要稳定到什么程度？

错误信息优先级很高已确认；可观察字段和快照稳定性还未定。

- **A（建议）：** 编译诊断至少包括稳定错误码、主源码范围、简洁原因、相关类型/调用点标签、可选帮助建议；自然语言文案可以改。运行时错误显示错误原因链、异常源、Task 创建点和 `await` 恢复链。CLI 提供适合脚本读取的 JSON 输出。
- **B：** 只把源码位置和可读文本作为契约，不承诺错误码或机器格式；首版更轻，测试不应锁定完整文案。

是否需要 LSP/编辑器协议作为标准工具链目标？诊断是否必须标注展开后的宏位置和映射回原声明的位置？

我的选择：A

### DIAG-02 · `check`、测试和发布产物纳入哪一份 RFC？

- **A（建议）：** 完整语言 RFC 定义错误类别和源映射；工具链 RFC 定义 `check/build/test/fmt/doc` 命令、测试目录格式和优化矩阵。标准一致性测试断言行为、错误类别和 span，不锁定自然语言句子。
- **B：** 把测试命令与快照格式也放进语言规范；一致性更强，但实现自由度更少。

首版必须有哪几个命令？你期待错误测试保存错误码/位置，还是整条消息快照？

我的选择：A

### STD-01 · 标准库的边界与发布节奏？

HTTP、JSON/TOML 属于标准库方向已确认；是否随 compiler 同步升级未决定。

- **A（建议）：** 核心 Runtime 和稳定基础库随工具链；HTTP/JSON/TOML 是官方维护、按需导入的库包，可独立发修复版；语法关键字仅用于无法由普通 API 表达的控制效果。
- **B：** 所有标准库都随编译器锁定版本；调用体验一致，升级库通常需要升级工具链。
- **C：** 工具链只提供异步/runtime 核心，HTTP 等全部独立发布；编译器较小，但用户安装步骤更多。

SQLite 首个绑定由官方标准库、示例包还是专门的 FFI 示例工程维护？标准 HTTP 至少应涵盖哪些协议/客户端功能？

我的选择：A

## 第六批：版本演进与 RFC 边界

### RFC-01 · 语言版本在 1.0 前如何变化？

- **A（建议）：** 0.x 可有明确迁移记录的破坏性变化；1.0 后语义兼容性由语言规范保证，标准库和包 API 分别做兼容承诺。
- **B：** 一旦 RFC Accepted 就不破坏；迭代慢但已采纳内容可立刻依赖。
- **C：** RFC 可独立标注 Experimental，允许在 1.0 前移除；Accepted 项只在声明稳定后有兼容保证。

哪些能力先标 Experimental（可能是宏、C ABI、并行域、格式映射）？废弃 API 至少保留多久？

我的选择：C

### RFC-02 · 哪些问题属于语言 RFC，哪些留给原型/工具链 RFC？

- **A（建议）：** 语言 RFC 固定用户可观察语义、类型检查与错误边界；工具链 RFC 决定 GC 供应商、LLVM lowering、包中心协议、部署矩阵与性能策略。仅当实现决定会改变语言可观察行为时，才回到语言 RFC 修订。
- **B：** 等 GC/LLVM/包中心都验证后再定语言规范；减少未来返工，但推迟一致性测试。

没有原型数据前，是否接受把 GC 收集器、目标 libc、默认 Worker 数和包中心签名协议明确标为“实现 Open”而不阻塞语言核心 RFC？

我的选择：A
