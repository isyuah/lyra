# 异步、错误与资源清理：一个请求结束时，会留下什么？

**先填 A-01～A-03**：它们决定普通 `spawn` 能做什么、谁负责收尾、库作者是否需要显式传上下文。A-04～A-07 可以第二轮再填。每题可写选项、自己的规则，或一段你希望能运行的代码；留空表示待讨论。

你明确想要的是内置异步，以及不必像 Go 那样沿调用链手传 `context`。[原草稿](../RFC_draft.md) §2、§3 把「`Result` 与异常并存」「调用 `async fn` 得到冷任务」标为 Accepted；§3.6、§3.7 的任务组与隐式上下文是 Proposed。下文是备选规则，示例不锁定关键字或 API 名称。

## A-01 · 两次 `spawn` 能同时写同一个对象吗？〔先答〕

两个并发下载共用请求内的 `progress`。考虑每次下载结束后执行的这一步：

```lyra
taskgroup {
    spawn count_one(progress)
    spawn count_one(progress)
}
```

- **A｜推荐：普通 `spawn` 继承当前串行执行域。** 两个下载可以同时等待网络，但同一个域同一时刻只执行一段用户代码。若 `count_one` 仅执行 `progress.done = progress.done + 1` 且中间不挂起，退出组后计数从 0 变为 2。不同执行域可并行；跨域只允许传递可安全共享的值，例如不可变数据或有同步保护的句柄。这条边界也要覆盖全局变量和隐式上下文，不能只检查函数参数。好处是普通请求代码不用锁；代价是要把 CPU 密集工作显式交给并行执行域，或让服务器把独立请求分配到不同域。
- **B｜普通 `spawn` 就可跨核并行。** 编译器在并发边界拒绝共享普通可变对象；上例要改用受同步保护的计数器，或让两个子任务返回增量、由父任务汇总。CPU 工作不需要另一套入口，但请求内共享小对象也要遵守这套规则。
- **C｜普通 `spawn` 可跨核，也允许直接共享普通可变对象。** 给锁还是用原子计数，由作者决定。上例可以编译，但无同步的 `+ 1` 不能承诺得到 2。它最接近 Go 用户熟悉的调用方式；代价是错误更晚暴露，检测器也只能发现实际跑到的竞争。如果选它，还要为有竞争的程序定下内存安全底线，例如字符串的地址和长度一起被读写时，不能草率地把行为交给 LLVM 的普通读写。

这里有两条独立的界线：**任务能否同时执行用户代码，以及并行时谁检查共享。** 即使选 A，同一执行域也可以换系统线程；跨 `await` 的读改写也不是原子的：两个任务若都在读到 0 后挂起，恢复后仍可能都写回 1。

我的选择：A

## A-02 · 一个冷任务是一份共享结果，还是一张只能用一次的票？〔先答〕

```lyra
let work = fetch(next_id())
taskgroup {
    let handle = spawn work
    let first = await handle
    let second = await handle
}
```

- **A｜推荐：同一个任务只执行一次，可以再次等结果。** `next_id()` 在第一行求值一次；`fetch` 的函数体到首次 `await` 或 `spawn` 才开始。直接 `await` 冷任务由当前作用域负责完成；`spawn` 把任务交给当前任务组，句柄丢弃不解除这份责任。后续 `await` 观察同一次成功或失败，重试须重新调用 `fetch`。代价是只要句柄还可等待，结果就可能一直占内存。若支持不可复制的资源结果，应另设单消费者规则，而非把独占资源发两份。
- **B｜冷任务及其完成结果都只允许一个消费者。** 第二次等待应报错；需要多个观察者时先显式共享一个可共享的结果。资源移交清楚，调用方多记一个规则，编译器或运行时也得识别重复消费。

推荐为单独写一行 `fetch(id)` 并直接丢弃的情况给出诊断，指到调用并提示 `await` / `spawn`。未启动的任务没有运行函数体，连体内的 `defer` 都没注册；调用参数已产生的副作用仍然有效。若你希望调用本身就启动网络请求，请标「重议冷任务」，这会改动草稿 §3.1，而非仅调整句柄 API。

我的选择：A

## A-03 · 在 A 创建、B 启动、C 等待：超时和日志跟谁？〔先答〕

```lyra
let work = with Task.scope(trace: "A") { fetch(42) }
with Task.scope(trace: "B", timeout: 2.seconds) {
    await work
}
```

- **A｜推荐：首次激活绑定上下文。** 上例的网络请求属于 B，日志带 B；B 取消时请求也收到取消。子作用域的有效截止时间取父期限和本地期限中更早的那个。好处是任务在哪个请求里真正运行，就由哪个请求负责；代价是仅从异步函数被调用的位置看不出最终 trace。
- **B｜拆开生命周期和诊断来源。** 所有者、取消和 deadline 仍随 B，trace 或少量明确声明的任务局部值在创建时从 A 捕获。适合「A 接单、B 执行」；日志能追到接单者，但两个阶段看到的上下文会不同。

**已经启动的任务是另一回事。** 若 C 用自己的短超时等待 B 已拥有的句柄，推荐只取消 C 的等待，不抢走所有权或取消 B 的工作；B 本身到期则取消 B 的子任务。若你希望 A 也始终拥有任务，请写明 A 已结束、B 此时才启动时该发生什么。

我的选择：A

## A-04 · 从调用点能看出哪些失败？

例如 `async fn find_user(id: Int) -> Result<User?, DbError>`。在同样返回 `Result<…, DbError>` 的调用方中，`let user = (await find_user(id))?` 应怎样区分「没有这人」「数据库拒绝请求」「库内部状态损坏」？

- **A｜推荐：前两种分别是 `Ok(null)`、`Err(DbError)`；内部不变量损坏走异常。** `await` 恢复结果或传播任务异常，随后 `?` 只传播 `Err`，保留原始错误。不匹配的错误类型先显式映射；`?` 不猜测如何把数据库错误变成 HTTP 错误。代价是业务边界偶尔要写一行转换。`Err` 是正常返回的值，任务组不会因此擅自取消兄弟。
- **B｜双机制仍保留，但标准库的 I/O 默认抛异常。** 正常路径更短；调用者要查签名约定或文档，才知道哪些异常值得恢复。请举一个你希望「必须处理」与一个希望「默认冒泡」的例子，作为分界线。

推荐把普通未捕获异常保留到 `await` / 任务组边界；若最终逃出程序入口，再输出带源位置的错误并非零退出。取消是否进普通 `catch` 由下一题单独决定。

我的选择：A

## A-05 · 取消请求发出后，普通 `catch` 能把它吞掉吗？

- **A｜推荐：独立的协作式取消。** 等待内置 I/O、可取消的挂起点或显式检查时响应；`catch Exception` 不拦它，退出时仍清理。在明确的限时操作边界可以把**该边界自己的**超时转成可处理结果，不能把外层请求的取消也转成「业务成功」。与之相对，远端服务主动返回超时响应，完全可以是本地 API 的 `Err`。
- **B｜取消是一种普通可捕获异常。** `try/catch` 一套机制即可；宽泛捕获并重试的库可能让终止中的请求继续跑，需要专门的诊断或强制重新抛出规则。

两种都按协作式讨论：不检查取消的 CPU 循环不会凭空结束。阻塞调用应走隔离的执行入口；若底层没有取消接口，移出 I/O 工作线程只能保护其他请求，不能让该调用立即停止。任务组仍要等它安全结束。

我的选择：A

## A-06 · 并发加载头像和订单，一边失败，另一边怎么办？

- **A｜推荐：未处理的子任务异常触发整组收尾。** 先请求取消仍在跑的兄弟，等所有子任务（含清理）结束，再从 `taskgroup` 报告失败；即使对应句柄从未 `await` 也一样。已经发生的其他异常一并保留，不依赖调度先后来丢弃错误。若头像是可选项，应在头像子任务内处理成默认头像或 `Result`。单独取消某个子任务与子任务抛异常分别处理，前者默认不连带兄弟。
- **B｜默认让彼此独立的子任务跑完，再汇总结果/异常。** 容易产出部分成功的页面；若它们本来就必须共同成功，一边失败后另一边仍可能占着连接。也可选 A 作默认、B 作显式的监督模式。

两个方案中，父请求本身被取消都应向下传播，退出组前等到收尾。长期后台工作若是刚需，请写下能拥有它并接收未处理错误的实体（例如整个服务的根任务组）。

我的选择：A

## A-07 · `defer` 能否挂起？清理自己失败又算谁的错？

- **A｜推荐起点：`defer` 做同步收尾。** 每个已经注册的清理在离开所属块时按注册的逆序各跑一次，包括正常返回、`?`、异常和取消。需要等对端确认、且失败会改变业务结果的 `flush` / `commit` 写在正常路径显式处理；`defer` 负责同步释放本地句柄。同步规则简单，但若协议要求所有退出路径都异步关闭，它就不够用。
- **B｜允许专门的异步清理块。** 它可以在退出时 `await close()`；好处是异步协议在异常路径也能完整关闭。要同时确定外层取消后清理还能等多久、到期如何结束，避免请求无限卡在收尾阶段。

两种方案都建议写明错误优先级：已有异常或取消时保留它作主因，清理抛出的异常作为附加原因，其余清理仍执行；普通返回（含 `return Err(...)`）本来没有正在展开的异常，此时清理抛错会接管这次返回。如果不接受业务错误被清理异常遮住，请写下期望上报的两条信息。

我的选择：先A

## 填完后，如何判断实现写对了？

以下仅按推荐项演示，选项改变就改预期。它们可以替换原草稿 §9 里「按规范正确传播」一类尚不能直接执行的描述。

| 场景 | 可观察的预期 |
|---|---|
| `fetch(next_id())` 创建后先不启动，随后对同一任务等待两次 | 创建后参数计数为 1、网络调用计数为 0；两次等待结束后网络调用计数为 1。 |
| A 创建、B 启动；C 等待同一句柄时自己的期限先到，B 仍有效 | 假时钟推进到 C 的期限后，C 退出等待；B 记录的 trace 仍为 B；放行测试 I/O 后，B 可拿到结果。 |
| 两个子任务都已注册清理并挂起；让其中一个抛异常，两个句柄都没人等待 | 另一子任务在取消点退出；离开任务组时两个清理都已各执行一次，父任务能看到原异常。用可控挂起点同步，不靠真实睡眠猜顺序。 |
| 裸写 `fetch(42)` 丢掉冷任务 | 诊断定位在源代码的调用表达式，并区分「现在等结果」与「交给任务组并发运行」两种修复意图。 |

参考对照：[Kotlin 的协作式取消](https://kotlinlang.org/docs/coroutines-cancellation.html#cancellation-is-cooperative)说明 CPU 循环为什么要主动检查；[Python 的 TaskGroup](https://docs.python.org/3.13/library/asyncio-task.html#task-groups)展示了一个子任务异常后取消其余任务，等全部退出再汇报错误的设计。两者是 A-05、A-06 的对照，不是 Lyra 已采纳的规则。
