## G-01 · 哪个真实程序最值得用它重写？

**建议拿一个你自己会部署、也愿意长期维护的程序当标尺。** 如果没有现成项目，我推荐一个小 HTTP 服务：根据 ID 并发读取两份数据，区分「没有这条记录」和「读取失败」，客户端断开时要能取消，最后把一个可执行文件拷到服务器。它能同时检验你关心的写法、异步、报错和交付；不用先发明一整套 Web 框架。

如果你更常写 CLI、爬取与批处理、或者包一层现有 C 库的工具，写那个反而更好。最好再贴 **5～15 行你希望亲手写的代码**，任何混合语法都可以；或者贴一段现有代码，说哪两行最想省掉。这个程序是设计样例，不意味着编译器第一次提交就得能跑 HTTP。

我的选择：这个我不知道啊

## G-02 · 新机器装完工具链，哪些事应该开箱就能做？（可后填）

你提到「做成库最后也得我维护」。这里有两个独立的问题：**谁维护、用户装完有没有**，和**它是不是语言关键字**。例如可以让 `await` 由编译器理解，让取消和截止时间由运行时沿任务传播，让 `timeout { … }` 只是随工具链交付的标准库函数。用户仍然不用装第三方包或层层传 `context`。

**建议：** 把任务、取消和基础 I/O 的共同规则写进规范；工具链自带构建、测试和基础标准库。HTTP、JSON、数据库绑定按 G-01 的实际需要区分「必须随工具链有」「官方维护、按需安装就行」和「能用 C 库即可」。都随工具链发最省用户配置，但这些库的更新也会与工具链发版更紧密；单人维护尤其值得划清这条线。

我的选择：按你的建议来,就是异步这种如果关键字更好用可以设计关键字,而http JSON 这种都属于标准库的内容.

## 读完草稿，我会怎样使用它

**直接沿用你的目标：** 写业务代码的手感、出错时能快速定位、内置异步、模块与包能支撑长期组织代码；产物走 LLVM 原生 AOT，不靠 VM 分发。可以带运行时，GC 优先采用现成实现，性能向 Go 看齐。二进制大小和多个服务进程的实际内存开销分开量。

**保留草稿的来历：** §12 已把值 `struct` / 引用 `class`、`Result` 与异常、冷任务、混合泛型生成、GC 抽象、Attribute 与 AST 宏、默认非空七项列为 Accepted。先以这些为讨论起点，不把它们整体降级，也不把各节里的 Proposed 顺手升为定案。如果你填的答案会推翻其中一项，下一版应点名「替换哪条、为什么、哪些示例和测试跟着变」。

下面几处值得先拆开，否则很容易写出两套都自称符合 RFC、行为却不同的编译器：

| 草稿里的线索 | 需要落到可观察行为的区别 |
|---|---|
| §1.5 允许 `let` 引用可变对象；§3.3 允许 Task 换 Worker 恢复 | 换线程恢复与两个任务同时修改同一个对象是两件事。先定 A-01，才知道编译器是否该拒绝共享，以及 `await` 后哪些类型收窄还有效。 |
| §2.2 的 `?` 展开原样返回 `Err(error)`，但示例由 `ParseError` 进入 `Result<Server, Error>` | 这个 `?` 要么需要定义错误类型之间的关系或转换，要么示例得显式转换。否则最想推广的写法反而没法测试。见 A-04。 |
| §4.1 把泛型语义与生成策略分开；§4 标题和 §12 又把「混合生成」列成 Accepted | 建议把「不同策略下类型和行为一致」作为语言承诺，把混合生成作为编译器方向。这样第一版可以先只做一种正确实现，不必推迟泛型功能或推翻用户代码。 |
| §6 把 `@route`、`@derive` 和 DSL 放在同章；P0-12 还没定义模块的公开边界 | 路由元数据、生成方法、拦截每次函数调用是三种不同需求。先用 L-07 选真正需要的效果，再按 M-02 确定生成声明归谁、对谁可见。 |

## 答完之后怎么定稿

1. **先写用户能观察到的规则。** 用 G-01 的程序和一两个反例起草下一版 RFC：正文写确认的默认行为，替代方案和遗留问题单列。先把基础也补齐，例如求值顺序、闭包捕获、集合复制、模式匹配和模块初始化；示例写法最后才收敛为词法、语法和优先级表。
2. **把规则变成有判别力的测试。** 例如草稿 `ASYNC-005` 现在只写「按规范正确传播」。若采纳「首次启动继承上下文」，用 A 创建冷任务、B 启动，断言任务内读到 B 的 trace；若选择创建时捕获，预期就应是 A。再写一个应被拒绝的程序，标出诊断位置和理由，而不锁死整句文案。
3. **规范和测试设计先行，实现按小块交付。** 模块身份与公开接口先于包中心，取消与清理先于调度器优化，受管理引用的寿命先于 C 回调。编译器首个纵向样例可以很小：分别对一个有类型错误和一个合法的程序给出源码诊断、以及经 LLVM 链接后能独立运行的产物。GC、异步和 FFI 再用第 04 卷的交叉场景验收。
