# 原生交付：编译器、运行时、GC 和 C 库

对应 [原始草稿](../RFC_draft.md) §0.3、§2.7、§5、§8.9、§9.3。直接用 LLVM 做 AOT 后端、应用不依赖语言虚拟机、初期复用现成 GC，这三件事按你的意愿往下设计。本卷问的是**你要在哪儿运行什么程序、什么算好用**；不要求你先懂 LLVM IR，或替编译器挑 GC 指令。

## N-01 · 把哪个文件拷到哪台机器，就算部署成功？（优先）

**建议：先指定一组真实的开发机和服务器。** 例如，如果你在 Windows 写代码，服务器是 Linux x86-64，可先在 WSL 或 Linux 上构建，拷一个可执行文件到约定了架构和 libc 基线的 Linux 上运行。目标机无需安装 Lyra、LLVM 或另一个语言运行环境。LLVM 支持某架构，不代表 Lyra 的链接器配置、GC、I/O 和 C 库已经支持该平台。

这里有两种不同的交付要求：「允许依赖目标系统约定自带的库」和「连这些动态库也不能依赖，空镜像里就能跑」。**建议先选前者，Lyra 运行时随程序链接；额外的 C 动态库必须能列出来。** 后者能简化容器部署，但每种原生依赖都得有合适的静态构建。若原生 Windows 开发、Windows → Linux 一键交叉编译、ARM 服务器或空镜像是刚需，请直接写进来，优先级会不同。

我的选择：开发机Windows,但是有WSL,部署机Linux,允许动态链接,如果可以的话,以后能逐步支持类似GO那样的scratch也可以,支持不了就算了
（开发机 / 实际部署机 / 允许依赖什么 / 是否必须交叉编译）

## N-02 · 一台服务器上跑很多小程序，最先碰到的限制是什么？

“几到十几 MB 可以接受”和“开几个服务也跑得动”要分开测：二进制放在磁盘上，而常驻内存还包括堆、线程栈、映射和 I/O 缓冲。**建议保留 Go 作参照，先测同负载，不先写一个没测过的硬上限。**

| 你实际关心的事 | 候选量法 |
|---|---|
| 发布包好不好拷、命令启动快不快 | 记录 Release 小 CLI 去调试符号后的文件大小、额外动态库和从启动到退出的耗时，分别报告 |
| 能不能同时养多个小服务 | 相同机器、相同数量的进程、相同请求量：分别记录空闲和负载下整组进程的内存。Linux 可用独立 cgroup 的内存计量；单进程 RSS 另列，不把共享页重复相加当作物理内存 |
| 服务跑起来是否足够快 | 同一请求处理逻辑写一份 Go 对照，在同一核数、并发量和持续时间下测吞吐、尾延迟和峰值内存 |

如果只能重点优化一个，**建议按你描述的部署场景先看多进程常驻内存**；如果实际是短命令频繁启动，优先级应反过来。取舍很具体：较大的堆和更多 Worker 有时能换吞吐，却会吃掉多开服务的余量。

我的选择：这不好回答,反正我们采用类似GO的方式内置RUNTIME和GC肯定达不到C的内存和程序包体大小,但是也不至于和虚拟机一样的内存占用,就这种折中的生态位感觉就可以

## N-03 · 如果第一版只能绑定一个真实 C 库，你选哪个？（用到 FFI 时优先）

一个最能指导设计的答案是「库名 + 一次实际调用」，而不是一串 C 类型。以下两种 API 都叫 C ABI，所需能力差很多：

| 实际用法 | Lyra 需要解决什么 |
|---|---|
| `compress(input, len, output, capacity)`，返回就不再持有缓冲区 | 长度与布局匹配；缓冲区在调用期间有效。可先复制到原生缓冲区，代价是一次拷贝 |
| `subscribe(callback, userdata)`，以后可能从外部线程回调 | 谁保活 `userdata`、何时注销、注销后是否仍有在途回调；回调线程如何接入运行时，错误怎样在边界内转换 |

**建议：用一个安全的 Lyra 封装包住显式的 FFI 声明；首版做所选库真实需要的那一层。** C 长期保存上下文时，若 API 接受不透明 `userdata`，可用显式注册、释放的句柄保活；若 API 需要解引用真正的 C 结构体指针，则提供具有相应布局和寿命的原生内存。普通 `String`、泛型对象、语言异常都不应碰巧以某种 LLVM 表示就直接越过边界。阻塞的 C 调用还要和调度器约定隔离方式；取消 Lyra 的等待并不会自动停止 C 代码。

怎么取得并链接这个库、是否允许包执行构建脚本，是 [模块与包卷](03-modules-packages.md) M-07 的问题；这里先定调用时的行为。

我的选择：（库 / 要调用的 API；是否阻塞、是否保存传入的数据、是否回调。不知道的写库名即可）首版选 sqlite3（典型调用：sqlite3_open / sqlite3_exec / sqlite3_step）。属于同步阻塞调用 + C 内部持有连接句柄（暂不涉及外部 C 线程反向回调 Lyra 闭包，能极大降低首版 FFI 与调度器复杂度）。

## N-04 · 遇到错误时，你最不想靠猜的是哪一步？

下面是**诊断草图**，语法与文案尚未定稿。假设 `load_user` 是返回 `User` 的异步函数，调用者也在异步函数里：

```text
let user = load_user(id)
user.name
^^^^
无法在 Task<User> 上读取字段 name。
  来源：load_user(id) 创建的是任务，等待它才得到 User。
  如果这里要读取用户：let user = await load_user(id)
```

**建议：命令行 `check` 先做到主错误定位到源码、交代类型从哪来、建议符合当前上下文；不必链接就能反馈。** 在此基础上，优先补哪一种体验？例如：① 服务抛错后能沿 `await` 找到发起调用的源码；② 编辑时就地看到类型和错误；③ 链接 C 库失败时直接指出缺的库和目标平台。我的建议是常写服务先选①；它需要为异步任务保留来源信息，有运行时和调试信息开销。② 则更早需要稳定的编辑器接口和增量反馈。也欢迎贴一条你在其他语言里最讨厌的报错。

## 实现建议：由原型验证，不交给你投票

| 边界 | 建议怎么做 | 为什么现在就关心 |
|---|---|---|
| 编译器与 LLVM | 源码与位置 → 名字解析 → 类型检查 → 带类型和控制流的中间表示 → LLVM IR → 目标文件 → 链接运行时。先让 `check` 止于前端；在交给 LLVM 前，把 `?`、清理和 `await` 的源语言含义确定下来 | 同一份类型与源码位置信息可服务于诊断和代码生成；用户不需要看 LLVM 的内部类型错误 |
| 运行时与现成 GC | 可先试用非移动、保守扫描的 BDWGC。运行时负责把全局对象、调度队列、暂停的任务帧、闭包以及 FFI 句柄里的活引用放在收集器看得到的位置，并处理线程接入 | 保守扫描可能把恰似地址的数值当成引用，从而多保留内存；反过来，只把最后一份引用放进普通 C `malloc` 缓冲区，收集器可能根本看不见 |
| 源语言与回收算法 | 保证对象身份、可达性和资源清理规则，不承诺对象地址永久稳定，不用终结器关文件。不要把「有 GC 接口」当成已经支持任意 GC | 如果以后改用精确移动式 GC，需要重新验证对象布局、活引用位置、移动后的引用更新和 FFI；LLVM 的 statepoint 是候选技术，不是今天必须承诺的语言特性 |
| 调度与 I/O | 语言层定义任务何时启动、何时能被取消；运行时负责调度、定时器与 I/O 唤醒，标准库提供好用的 API。是否允许普通任务并行按 [异步卷](02-async-errors.md) 的答案来 | `await` 可以让出执行线程，但底层阻塞 I/O 不会因为函数前面写了 `async` 就变成非阻塞 |

**进入实现时的第一批验收场景**（现在是设计输入，还没有运行结果）：

- **交付：** 在 N-01 指定的干净目标系统上只放承诺的产物，运行一个打印并退出的程序；若用了外部动态库，再核对产物声明的依赖。
- **GC × 异步：** 让一个对象只通过仍被调度器持有的暂停帧可达；在测试运行时触发回收，再恢复任务读回原值。分别用 `O0`、`O2` 构建，不用「某个不可达对象应在几毫秒内消失」作断言。
- **FFI：** 针对 N-03 所选 API 做一进一出的真实调用；若支持保留回调，再测等待期间发生 GC、回调和注销后释放句柄，包含外部线程接入路径。
- **诊断：** 对 N-04 的程序断言拒绝编译、主位置和 `Task<User>` / `User` 之差；另给加上 `await` 的合法示例。断言该解释清楚的事实，不锁死中文标点。
