# 模块与包：从两个本地包到发布

对应 [RFC 草稿](../RFC_draft.md) §0.3、§8.8、P0-12，以及规划中的 RFC-0008 / 0011。草稿要求模块和包有稳定身份，也要求宏生成的公开声明能找到所属模块；文件怎样组成模块、依赖怎样定版本，都还没有定。下文的文件名、语法和命令只是候选。

**先填 M-01、M-02、M-04。** 它们决定源码如何拆分、什么算公开 API，以及两个库能否一起使用。每题可以填「采用建议」、改写成你想要的行为，或写一个建议方案满足不了的例子。

## 用同一个工程回答

假设你在写一个小服务 `server`，其中的网络配置代码 `acme/config` 以后可能独立发布：

```text
service/
  lyra.toml                 workspace：成员为 server 和 config
  server/
    lyra.toml               包 acme/server；依赖 acme/config，本地简称 cfg
    src/main.ly
  config/
    lyra.toml               包 acme/config
    src/net/model.ly        声明 Endpoint
    src/net/defaults.ly     声明 localhost()，返回 Endpoint
```

```text
import cfg.net.Endpoint
import cfg.net.localhost

fn default_endpoint() -> Endpoint { localhost() }
```

这里 **模块** `net` 管源码中的名字和可见性；**包** `acme/config` 是声明依赖和发布版本的单位；**workspace** 把两个本地包放在一起开发，不自动授予互访权限；**包中心**存储、索引已发布的版本，不参与解释 `import` 语句。

## M-01 · 拆一个文件，要不要改调用者的导入？（优先）

**建议：一个目录一个模块。** `src` 是包的源码根，同目录文件共享模块内的声明。在 `net/` 内把 `Endpoint` 从 `model.ly` 挪到 `address.ly`，上面的两个 `import` 不动；把它挪到另一个目录，模块路径才改变。跨包导入从清单里的依赖简称起步，不从磁盘路径起步。

代价是同目录的文件共用命名空间，两个同名声明必须报出两处位置。若希望每个文件自带边界，可以选「一文件一模块」；若希望目录移动也不改变模块名，可以在源码中显式写模块名，代价是文件树与模块树可能不一致。

我的选择：A,一个目录一个模块,以及支持显式Re-export

## M-02 · 什么样的声明能被另一个包使用？（优先）

**建议：无标记只在本模块可见，`internal` 在本包可见，`pub` 才能跨包导入。** 因此 `defaults.ly` 可以访问同在 `net/` 的私有辅助函数；隔壁的 `server` 即使在同一 workspace，也只能看到 `pub`。普通 `import` 不会替别的包再导出符号。宏生成的声明走同一套规则。

按这个方案，若 `localhost()` 是 `pub` 而返回的 `Endpoint` 是 `internal`，在 **config 自己编译时**就指出公开签名与隐藏类型两处位置。另一种做法是只由包入口列出对外导出项：内部迁目录时容易维持 `cfg.Endpoint` 这样的稳定入口，代价是要维护导出表。哪种更符合你维护库的习惯？

我的选择：默认只在同模块可见,pub可以被导入,支持纯别名pub,比如pub A = B,包括类型和函数常量的rename,别名公开的是纯别名,非独立类型,禁止“通过类型别名给私有类型提权”,以及报错方面的报错信息优先还原别名

## M-03 · 导入一个模块，会不会让它开始干活？

**建议：导入只引入名字。** 顶层允许声明和可在编译期求值的常量；打开文件、连数据库、注册路由等动作由入口显式触发。同一包里的两个模块可以在函数签名中相互引用，不会因此争抢“谁先运行”。常量 `a = b; b = a` 仍应报告求值环；两个包互相依赖也应拒绝并列出依赖路径。

好处是加一个 `import` 不会悄悄启动后台任务；代价是插件要有明确的注册入口。如果确实想要“导入即注册”，请写下场景，尤其是注册失败时你希望谁接到错误。

我的选择：导入只引入名字

## M-04 · 两个依赖需要同一个库的不同大版本，能否一起用？（优先）

假设 `server → config → text 1.x`，另一条路径是 `server → logger → text 2.x`。**建议：同一可执行程序中，每个包只选一个满足各方约束的版本。** 发布包按「来源中心 + 完整包名」识别，`cfg` 这种本地简称不创建新身份。上述约束无交集时，构建失败，诊断并排列出这两条依赖链；一个库改了简称也不能绕过冲突。

代价是即使两条路径只在内部使用 `text`，也可能要等一个上游更新才能构建。若选「不同版本可并存」，升级会容易些，但假如 `text` 声明了名义类型 `Token`，就必须区分来自 1.x 和 2.x 的 `Token`；上游把它暴露在公开签名里时，诊断须讲清是哪两个包实例。

我的选择：按建议,只能选取一个版本

## M-05 · 明明没改代码，明天再构建能自动换依赖吗？

**建议：已有锁的构建沿用它，升级由开发者主动发起。** 清单写允许的版本范围，workspace 的一份锁记录实际解析的依赖图、来源、确切版本和发布内容摘要。库自己的锁用于开发和测试；被别人依赖时，使用最终工程的锁，而不是让每个库各带一张版本表。

代价是要提交、审查锁文件，以及主动获取修复版本。候选 `--locked` 在缺锁或清单与锁不符时直接失败；它仍可下载锁里写好的包。`--offline` 才禁止联网：本地缺少锁定的包时，应点明缺谁。锁在这里保证**选中同一批依赖**；若还要求产物逐字节相同，工具链和目标平台等输入也得固定。

我的选择：按建议

## M-06 · 本地能用的包，怎样搬到包中心？

**建议：本地先能完整工作，中心是后加的来源，不是开发前提。** workspace 显式绑定 `cfg` 到本地 `acme/config`；发布后可将同一依赖绑定到中心版本，`import cfg.net.Endpoint` 不改。优先分发带清单的源码包，由使用方的工具链编译，这样泛型定义可以跨包使用，无须先承诺稳定的 Lyra 二进制 ABI。

发布时拒绝仍含“作者机器上的本地路径”、却没有可发布来源的依赖；中心的同名同版本内容不可覆盖，修复走新版本。代价是首次编译要花时间，也无法靠这种模式分发闭源库。**如果只发二进制、仅用私有中心或不经过中心交付源码是你的必需场景，请注明。**

我的选择：分发源码包,本地可以工作,禁止发布依赖本地依赖的,禁止覆盖版本,就是按照建议

## M-07 · 引入一个绑定 SQLite 的包，构建时允许它做什么？

**建议：原生依赖优先声明，第三方包默认不能执行任意安装脚本。** 包按目标平台声明要链接的 C 库、可用的静态或动态形式，以及随包提供的源码或制品。工具链负责已支持的编译和链接步骤；使用系统动态库时列出运行所需的库。这样“直接部署”有可检查的含义：是只带可执行文件，还是还需 `sqlite3` 动态库。

代价是遇到只能靠定制脚本编译的 C 库时，需要用户另行准备，或由项目显式授权构建步骤。若你愿意为“一条命令装好”放宽这个边界，请举一个库，并写下你能接受它在构建机上做什么。本题只谈如何获得和链接库；C 调用约定、回调与 GC 句柄归原生运行时设计。

我的选择：希望可以声明需要执行脚本,但是默认不执行,而是列出和提醒用户,通过单独的命令执行安装脚本.
