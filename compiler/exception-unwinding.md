# 普通异常如何越过 Lyra 调用，而不穿过 C

[错误与资源 RFC](../rfc/errors-and-resources.md)区分普通异常、`Result::Err`、任务取消和致命故障。下文是建议的编译器协议；目前已实现并独立验证的是 `runtime/exceptions.h` 中的异常载荷和报告，尚未接入 `throw`、`await` 或 `defer`。普通 C 错误或 `lyraTaskFail` 的原生指针必须经过显式适配才能交给 Lyra `catch`。

## 同步的最小闭环

先支持内置 `Exception(message: String)`、`throw expression`、兜底 `catch { ... }`、在 catch 内单独 `throw`。若提供 `catch (name: Exception)`，`name` 只在该处理块可见。`try` 是表达式：正常路径与 catch 中正常完成的分支需要有相同的目标类型；`throw` 类型为 `Never`。过滤条件和自定义异常子类型不应靠匹配消息字符串来模拟。

建议私有 Lyra 调用约定在普通函数最后加一个异常输出槽，保留原有的正常返回值类型。调用者初始化为空；正常路径读取函数值，异常路径只读取异常槽。`throw` 生成 LLVM 分支：展开本函数内应退出的块，跳到最近的处理器；若未命中则写出异常并从当前函数返回。调用方检查该槽后才消费普通返回值。默认实参的内部函数和隐式转换也是真正的调用，适用同一约定；无异常路径后续可通过 LLVM 优化移除检查。

捕获时把当前异常从槽中取出，放在 catch 自己的绑定中，再清空槽。这样处理块可以成功返回，也能抛另一异常；裸 `throw` 传播同一异常而不是创建一个新抛点。未被捕获的普通异常由入口打印并非零退出。原生 `extern` 包装仍只按已声明的 C 签名传参；C 不看到异常槽，不让 `longjmp` 或 C++ 异常穿过回调边界。

## 等待和清理的边界

- **Task 的终态属于 Task。** 成功返回值、普通异常、取消须有不同标记。`await` 已失败的 Task 应让等待者的 LLVM 状态机恢复到普通异常分支，而不是直接终结等待者或把 `void* outcome` 当作成功值加载。取消仍进入取消分支，跳过全部普通 catch。
- **重复或跨组等待。** 保存异常的最初位置和已在任务组汇总的所有失败。为每个等待者添加自己的 `await` 位置时使用独立记录，不改写 Task 缓存的终态、归属或另一等待者的栈。激活模式决定失败走哪条路：直接等待冷 Task 走调用链，捕获后不另行组汇总；未观察的 `spawn` 走组汇总，跨组等待者不接管原组责任。三个可独立验收的场景见[异步 RFC](../rfc/async-execution.md#已接受验收行为)。
- **阻塞工作线程。** 闭包可以同步抛异常，原生工作回调正常返回带标记的完成结果，由执行域发布终态。工作线程不能跳回等待者的 native stack，线程局部变量也不能代替逻辑 Task 的状态。
- **`defer`。** 每个同步清理回调也要能把异常作为普通 C 返回值交回清理循环。循环在每次调用前弹栈，按逆序继续运行剩余清理。正常完成（包括提前返回 `Err`）时，首个清理失败成为主异常；展开异常或取消时保留原主因，按实际执行顺序附加所有清理失败。取消的附加原因保留在取消结果中，不把取消改造成可被 `catch` 吞掉的普通异常。

异常报告使用 GC 管理的不可变记录：消息、最初 `throw` 位置、普通/异步调用位置和附加失败。一个等待者附加调用帧或附加失败不会修改别人的记录。报告遍历不递归使用原生调用栈。传给运行时的文件名和帧标签必须是由编译器保留的静态 C 字符串，异常消息则是带显式长度的 Lyra `String`。

## 行为验收

1. 让异常跨两个普通函数到达 `try`；处理后继续执行，抛点之后的语句不执行。内层 catch 裸重抛时报告原抛点。
2. 让默认表达式抛异常：之后的默认值和被调函数体都不执行。让转换函数抛异常：不把它改成 `Result::Err`。
3. 正常块尾、显式 `return`、`?` 和已有异常分别触发两个会抛的清理：每个清理都执行且只执行一次，保留主因和所有次因。
4. 分别等待发生普通异常、返回 `Err` 和被取消的任务；只有第一者进入普通 catch。重复等待保留原抛点；忽略已启动子任务的句柄仍能观察组失败。
5. SQLite/native 工作在取消后安全返回，再释放资源；清理失败作为取消的附加原因报告，不越过 C 调用帧。
